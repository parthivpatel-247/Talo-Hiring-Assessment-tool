What was actually tested

This is not a static-page ping test. Each simulated student ran the complete, real flow, which is also where the database does its heaviest work: log in, start Part 1 (which assigns their randomized question set), answer each question with auto-save on every question and periodic heartbeats (the timer sync), submit Part 1, then start, answer and submit Part 2.

That is ~18 server calls per student, and it includes every database write the live system makes during an exam: logins, answer auto-saves, and heartbeats. Database write contention is the one thing that genuinely gets harder as more students join at once — so that is exactly what we stressed. To stay conservative, all students in each run arrived within a ~60-second window, a denser burst than a real drive where students trickle in over several minutes.

Reading the stress column: we deliberately kept raising the arrival rate until the system broke, to find the ceiling. On the local test machine that happened around 700–1,100 students hammering simultaneously. Even at that extreme the server degraded gracefully — requests queued and slowed, ~14% timed out, but the process did not crash and recovered as load dropped. That is the behaviour you want at the edge of capacity, and it is far beyond any realistic campus turnout.

Why this is conservative (production is stronger, not weaker)

The local numbers come from a single process on one CPU core with the database as a single local SQLite file — deliberately the worst case for write contention. Production is more capable in two ways that matter:

• Cloudflare Workers auto-scale across isolates. Each request runs in a lightweight isolate that Cloudflare distributes across its global fleet — there is no single-box concurrency cap to hit at 100 users.
• Production D1 is a managed database service, not a local SQLite file on one core. The real shared bottleneck in any such app is the database, and we stressed the harshest version of it locally — and it still cleared 500 students with zero errors.

So the local result is a floor, not a ceiling — and the production run confirmed the real edge handles the target cleanly. For reference, Cloudflare's documented Workers Paid / D1 limits (CPU 30 s–5 min, D1 up to 10 GB, 1,000 queries per request) sit far above what 100 students doing a few small writes each will ever touch.

How the production test was kept safe

The production run used 100 synthetic throwaway accounts (load-####, deleted afterwards), not real candidates — so no real student's account or one-test-per-email lock was affected, and the database was returned to its exact prior state. It was run outside any live assessment window. The candidate flow never calls the AI grader or resume storage, so the test added no AI/storage cost — only the genuine database write load, which is exactly what we wanted to measure.

AI (OpenAI) usage & cost per student

Talo uses OpenAI for three one-time, admin-side jobs only — reading the resume, writing each student's personalized Part 2 questions, and grading. The exam itself makes zero AI calls, so how many students take the test at once has no effect on AI cost. Model in use: gpt-4o-mini.

The PDF-to-text step runs locally (no AI, no cost). Uploading the resume itself is plain file storage, not an AI call. Part 3 is retired, so it adds nothing. Grading is the heaviest part — 5 of the 7 calls.

Cost. At gpt-4o-mini pricing ($0.15 per 1M input tokens, $0.60 per 1M output tokens) and typical resume/answer sizes, each student costs roughly $0.003–0.005 — under half a cent — for the entire pipeline (resume → questions → grading).

How to reproduce

Everything lives in the repo under loadtest/. Production 100-student run (seeds throwaway accounts, runs the full flow, cleans up):

# 1) seed 120 throwaway candidates on production
npx wrangler d1 execute campus-hiring-assessment-db --remote --file loadtest/prod-seed-100.sql
# 2) run the real 100-student spike against production
k6 run -e BASE_URL=https://talo.hevo-talo.workers.dev -e MODE=flow -e SCEN=spike -e POOL=120 \
  --summary-export loadtest/results/prod-spike-summary.json loadtest/candidate-flow.js
# 3) delete all throwaway data from production
npx wrangler d1 execute campus-hiring-assessment-db --remote --file loadtest/prod-cleanup.sql

Local runs (stress + headroom), no production impact:

bash loadtest/run-local.sh spike      # 100 students
bash loadtest/run-local.sh headroom   # 300 students
bash loadtest/run-local.sh mid500     # 500 students
bash loadtest/run-local.sh stress     # ramp until it breaks

In one line, for the manager

We load-tested the real production system with 100 students taking the full assessment at once: all 100 finished, zero failures, responses under ~1.1 seconds. We also pushed a local copy to 5× that load with no errors, and it only strained at 7–10×. Talo is ready for the campus drive.
